# AI Agent Workflow Automation

**Author: Kanish Mahato**

An agent that turns the 10 business workflows in `data/AI_Agent_Workflow_Assessment.xlsx` into executable
workflows. It understands a plain-English request, picks the right workflow, runs the Excel-defined steps through a
tool layer, handles conditions and errors, and shows **which workflow was selected, which steps ran, and the final result**.

It is **one generic engine + one small module per workflow**, not ten chatbots. Adding an 11th workflow is one Excel
row plus one new `.py` file (proved by an automated test, see [Adding a workflow](#adding-an-11th-workflow)).

```
User request
     |
     v
 Agent.handle ----------------- session: remembers a pending question so "ORD-1002" completes the same run
     |
     v
 WorkflowRouter ---- LLM tool-calling (each Excel row exposed as a function)  --or--  heuristic TF-IDF fallback
     |                       -> workflow id + extracted parameters + reason + confidence
     v
 resolve_params ---- user value > real default > bundled sample (always labelled in the output)
     |
     v
 WorkflowEngine ---- walks the Excel "Steps" column in order; each step is a bound Python handler
     |                       |  decisions recorded, NeedMoreInput / StepError / exceptions handled, steps timed
     v                       v
 Tool registry  <-- ctx.call_tool("csv_reader", ...)   permission check (Excel "Tools_Required"), retry, tracing
     |
     v
 RunReport -> text / markdown / JSON   + CSV / markdown result files + step-level execution log (feeds WF010)
```

## Quick start

Requires Python 3.10+ (developed on 3.12). The only dependencies are `openpyxl` and `pytest`; the LLM client uses the
standard library.

```bash
# macOS / Linux
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```
```powershell
# Windows PowerShell
python -m venv .venv; .venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

```bash
python -m workflow_agent "Which products need restocking?"     # one request (offline mode, no API key needed)
python -m workflow_agent                                        # interactive chat; follow-up answers work
python -m workflow_agent --list                                 # workflows as read from the Excel file
python -m workflow_agent --validate                             # Excel <-> code <-> tools consistency check
python -m workflow_agent --examples                             # run the 10 Test_Questions + 22 scenarios -> examples/outputs/
python -m pytest                                                # 170 tests
python -m workflow_agent "Where is order ORD-1001?" --json      # machine-readable result
python -m workflow_agent --workflow WF001 --param threshold=30 x   # skip routing, set parameters explicitly
```

### Enabling an LLM (optional)

Copy `.env.example` to `.env`. Any OpenAI-compatible endpoint works:

```
# OpenAI                                   # local Ollama
LLM_PROVIDER=openai                        LLM_PROVIDER=openai_compatible
OPENAI_API_KEY=sk-...                      LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=gpt-4o-mini                      LLM_MODEL=llama3.1
```

With an LLM the agent uses **tool calling** to choose the workflow and extract parameters, and uses the model for
WF004 / WF007 content and low-confidence WF008 keywords. Without one (or if it fails) everything still runs through
deterministic fallbacks and the output says so (`Routing: heuristic (LLM fallback)`, `generated by: template`).

## Where to look in the output

Every response prints, in this order: **Selected workflow** (+ routing method, reason, parameters and where each came
from) -> **Steps executed** (status, timing, what each did) -> **Conditions / decisions** (next to the Excel rule) ->
**Tools / API calls** (incl. retries and failures) -> **Warnings** -> **Result** (summary, tables, files written).

Saved examples of every workflow, plus clarification, retry, degradation and escalation cases, are in
[`examples/outputs/`](examples/outputs/README.md) (`.txt` as the console shows it, `.md`, and full `.json`).

## How the Excel file is used

`workflow_agent/excel_loader.py` reads the **Workflows** sheet into `WorkflowSpec` objects (id, name, trigger, inputs,
**ordered steps** split on `→`, decision logic, tools, expected output) and the **Test_Questions** sheet as routing examples.
Column headers are matched forgivingly; duplicate IDs, empty steps or missing columns raise one error listing every problem.

The workbook is the source of truth for **what** a workflow is (its steps and their order, the rule shown next to
decisions, the tools it may use, the text the LLM sees when choosing). Python supplies **how** each step runs. Binding
is by step text (`@wf.step("Load inventory")`), and `Agent` validates at startup that every Excel step has a handler,
no handler is orphaned, and every `Tools_Required` label resolves to a tool. If someone edits the workbook the app
fails fast with e.g. `WF001: Excel step 'tally' has no @step handler (closest handler: 'identify low-stock products')`.

## How the right workflow is chosen

1. **LLM tool calling** (when configured): each Excel row becomes a function whose description is built from the
   Trigger / Inputs / Expected_Output columns and whose parameters come from the workflow's declared inputs, plus a
   `no_matching_workflow` function. The model must call exactly one. Arguments are validated/coerced and anything not
   declared is dropped; the workflows' own extractors fill what the model missed.
2. **Heuristic fallback**: TF-IDF cosine similarity between the request and each workflow's text (name, trigger, inputs,
   outputs, decision logic, steps, Test_Questions examples, per-workflow `routing_hints`), plus a bonus when the
   workflow's own parameter extractors find evidence (an `ORD-1001` implies WF005).
3. Below a minimum score -> "no workflow matches" and a list of what the agent can do. A near-tie -> the agent asks
   which one you meant (reply `1` / `2`).

Measured on the offline router: 10/10 of the workbook's Test_Questions; 44/44 on a first set of paraphrases I wrote
while building it; on 23 harder phrasings I wrote afterwards it got 21 right at first (one wrong workflow, one confusing
phrase), then two generic fixes (an extra stop word, and indexing the Decision_Logic text) took it to 22 right with the
last one safely "no match" rather than wrong. That second set is therefore no longer a clean held-out test. Treat the
heuristic as a fallback; the LLM path is the primary one.

## The 10 workflows

| ID | Rule from Excel | How it is implemented (interpretations marked *) |
|---|---|---|
| WF001 Inventory Restock | `current_stock < minimum_stock` | strictly less-than, so stock == minimum is **not** flagged. Reorder qty* = `max_stock` (or 2 x minimum when absent/invalid) - current. Bad rows are skipped and reported. Optional global threshold from the request ("below 20"). |
| WF002 Price Validation | flag when difference > 10% | difference* = abs(vendor - internal) / internal, exact `Decimal` math, so an exact 10.00% is **not** flagged. SKUs matched ignoring case/space. Unmatched SKUs, bad prices and zero prices reported, no division by zero. |
| WF003 Vendor File | rows missing SKU or name are invalid | CSV or XLSX, header row auto-detected below title rows, column synonyms normalised, cleaned CSV + invalid-row report written. Bad prices / duplicate SKUs are *warnings*, not invalid, because the rule names only SKU and name. |
| WF004 Description Generator | do not invent missing attributes; mark missing | Model sees only supplied facts. Missing ones appear as `[NOT PROVIDED]` and in a "Missing information" table. Output is checked for length, placeholders and invented materials/colours/audiences; one retry, then a deterministic template. Only a missing *product name* stops the run. |
| WF005 Order Status | no order found -> ask for another identifier | Order id or email (many orders). Invalid id asks before touching the API. Shipment API retried automatically; if it stays down the status is still returned, with the gap marked. |
| WF006 Duplicate Detection | exact SKU = definite; high similarity = possible | "Exact" after normalising case/space/punctuation (`cat 004` = `CAT-004`). Names scored with Jaccard + sequence ratio, attributes compared; a conflicting colour/size/brand/material means *variant*, not duplicate. Groups get weakest-link confidence (definite / high / medium) with evidence. |
| WF007 Campaign Brief | if goal or dates missing, request them first | Step 1 stops and asks. So the sheet's request *"Create a campaign brief for the new collection."* **correctly asks for goal and dates**; answer in the next message and it completes. Audience/promotion are never invented and are listed under Assumptions. |
| WF008 Keyword Classification | informational / commercial / transactional / navigational | Rules first, LLM only for low-confidence keywords; each row records its source. Duplicates merged (max volume). Priority* = volume x intent weight, unmapped keywords capped at medium. CSV exported. |
| WF009 Task Assignment | prefer skills + capacity; escalate if none | Suitable = active, role matches, **all** required skills, enough free hours (pro-rated to the deadline). Ranked by skill proficiency vs free capacity (urgent weights capacity more). Otherwise **ESCALATE** with the near-misses and why each failed. |
| WF010 Performance Report | flag failure rate > 10% or slow average | `needs_input` runs are not failures. Thresholds configurable. Can analyse the bundled sample log or the agent's **own live log** (`--param live_logs=true`). Specific recommendations per error type / slow step. Numbers are cross-checked against an independent calculation in the tests. |

Several Test_Questions refer to "this product / this task / this spreadsheet". With no input supplied the agent uses the
bundled sample and labels it `[bundled sample]` in the parameters line (turn off with `ALLOW_SAMPLE_DEFAULTS=false`).
Explicit input always wins; providing any product field disables the sample product entirely.

## Tools and error handling

Tools live in `workflow_agent/tools/` and are the only way steps touch files, APIs or the LLM. A workflow may call only
the tools named in its own Excel `Tools_Required` cell (otherwise `ToolNotPermitted`). The registry gives every call
retry with back-off for transient errors, uniform error wrapping and tracing.

| Situation | Behaviour |
|---|---|
| Missing/invalid input | `NeedMoreInput` -> the agent asks; the next message completes the same run |
| Bad row in a file | skipped and reported, run continues |
| Missing file / required column | run fails with a clear message and a hint; remaining steps shown as `skip` |
| Transient tool failure (shipment API, LLM) | retried; if still failing, graceful degradation or template fallback |
| Unexpected exception in a step | caught, step marked failed, agent keeps running |
| LLM down / garbage reply | heuristic router / templates, stated in the output |
| Unknown request | "no match" with the list of workflows, or a which-did-you-mean question |

The simulated order and shipment APIs (`data/orders.json`, `data/shipments.json`) can inject failures: `ORD-1004`
times out once (retry succeeds), `ORD-1007` never recovers (degraded answer).

## Adding an 11th workflow

1. Add a row to the **Workflows** sheet (name, trigger, `a → b → c` steps, rule, tools, output).
2. Create `workflow_agent/workflows/wf011_something.py`:

```python
from workflow_agent.core.registry import WorkflowModule
from workflow_agent.core.models import Param

wf = WorkflowModule("WF011", params=[Param("product_file", "Product CSV", type="file", sample_default="data/products.csv")],
                    routing_hints=["how many products"])

@wf.step("Load products")                  # text must match the Excel step
def load(ctx):
    ctx.state["table"] = ctx.call_tool("csv_reader", op="read", path=ctx.param("product_file"))

@wf.step("count products")
def count(ctx): ctx.state["n"] = len(ctx.state["table"]["rows"])

@wf.step("report")
def report(ctx): ctx.set_result(f"There are {ctx.state['n']} products.")
```

Nothing else changes: workflows are auto-discovered, routing indexes the new row, tools and rendering are generic.
`python -m workflow_agent --validate` tells you if anything doesn't line up. A new tool is one decorated function in
`workflow_agent/tools/`. See `tests/test_engine_and_extensibility.py::test_adding_an_eleventh_workflow...`.

## Verification and honest limits

* `python -m pytest`: 170 tests, all pass, no network or API key needed. They cover every workflow's rules and edge
  cases (boundaries such as exactly-10% and stock == minimum), error paths, the Excel loader and startup validation,
  routing, multi-turn clarification, renderers, the CLI, and the 11th-workflow claim.
* The **LLM code paths were tested against a local fake OpenAI-compatible HTTP server** (real HTTP client, tool-call
  parsing, fallbacks, validation of invented content) and scripted stub models. **I did not run them against a real model.** Run
  once with your own key or Ollama before demoing; small local models may ignore `tool_choice` (the router then tries
  a JSON reply, then falls back to the heuristic).
* Business details the Excel leaves open (reorder quantity, percentage base, priority scoring, what counts as "suitable"
  for an assignment, log thresholds) are my interpretations, marked above and easy to change in one place.
* Data is synthetic. APIs are simulated. Keyword intent rules are English-only. Duplicate detection is O(n^2) for
  catalogues up to ~400 rows and switches to an inverted-index shortcut beyond that (not benchmarked at scale).
* Sample defaults are convenient for the Test_Questions but can mask a missing input; they are always labelled.

## Key decisions (short)

* **Custom lightweight engine instead of LangGraph/LangChain** - the flow is a linear, Excel-defined sequence with
  early exits, so a graph framework adds dependencies without adding capability here; engine/context/tool boundaries
  would map one-to-one onto graph nodes if needed.
* **Excel owns the process, Python owns the mechanics**, tied together by validated step-text binding.
* **LLM where judgement helps, code where correctness matters** (money math in `Decimal`, thresholds, validation); LLM
  output is checked and always has a deterministic fallback.
* **Everything observable**: decisions, tool calls, retries, timings and an execution log in the same schema WF010 reads.
